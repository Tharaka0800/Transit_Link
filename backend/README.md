# TransitLink backend

The Express HTTP server now serves the existing MongoDB-backed account and notification routes alongside Supabase-backed incidents. Socket.IO shares the same HTTP server and port. Both incident REST requests and socket connections use the app's existing JWT; all signed-in users retain access to the Officer dashboard.

## Setup

1. Use Node.js 22 or newer and run `npm install` in this directory.
2. In your Supabase project's SQL editor, run [db/schema.sql](db/schema.sql). It creates the table, newest-first index, and server-only access rules. It does not insert sample alerts.
3. Create an ignored `backend/.env.local` containing `SUPABASE_URL` and `SUPABASE_SECRET_KEY`. A legacy `SUPABASE_SERVICE_ROLE_KEY` is also supported. Use [.env.example](.env.example) as a reference. The workspace's existing `.env` is tracked, so preserve its current MongoDB/JWT settings and put new Supabase credentials in `.env.local`.
4. Start MongoDB, or retain `USE_MEMORY_DB=true` for the existing demo database. `AUTO_SEED=true`/`USE_MEMORY_DB=true` still seed the existing demo accounts and notifications.
5. Run `npm run dev` to start the TypeScript server on port 5000 by default.

The server loads `.env.local` before `.env`; externally supplied environment values take precedence over both. The Expo client uses only the Express server URL and its existing login token. See [Supabase's API key documentation](https://supabase.com/docs/guides/getting-started/api-keys).

For a production-style local build:

```bash
npm run build
npm start
```

The compiler includes the shared contract and legacy JavaScript modules, so the built entry is `dist/backend/src/index.js`. The older `node server.js` command is a compatibility wrapper and also requires a build first.

## Incident API

Send `Authorization: Bearer <login token>` on every incident request. Request bodies use camelCase; the repository maps them to PostgreSQL's snake_case columns. Responses use the shared `IncidentAlert` contract with UUID `id` and numeric `createdAt` in Unix milliseconds.

| Method | Path | Success response |
| --- | --- | --- |
| GET | `/api/incidents` | 200, incident array sorted newest first |
| POST | `/api/incidents` | 201, created incident |
| PUT | `/api/incidents/:id` | 200, updated incident |
| DELETE | `/api/incidents/:id` | 204, no body; deleting an absent UUID is harmless |

Example create body:

```json
{
  "busId": "154",
  "route": "CMB → KDY",
  "delayTime": "15m",
  "status": "URGENT"
}
```

PUT accepts any nonempty subset of these four editable fields. IDs and creation times are generated by PostgreSQL and cannot be changed through this API. Invalid requests return 400, a missing update target returns 404, and database failures return 500 with `{ "message": "..." }`.

## Real-time updates

Connect a Socket.IO v4 client to the server origin and provide `auth: { token: '<login token>' }`. Successful database mutations emit `incident_updated` with `{ action: 'created' | 'updated' | 'deleted', id: string }` to authenticated clients. Failed mutations and absent-row deletes emit no event.

The dashboard re-fetches the server's incident list on each event and after a connection/reconnection. Registering the listener separately from the `connect` handler avoids duplicate subscriptions. Events cover mutations through this Express API; edits made directly in the Supabase SQL editor are visible on the next fetch.
